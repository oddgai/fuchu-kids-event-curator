# 府中の子供向けイベント収集：設計案

状態：設計承認済み。初期セットアップを実施し、ローカルで検証済み。GitHub上のCI実行はpush後に確認する。

## 目的

家庭でのお出かけ先を探すため、府中市と近郊のイベントを定期的に集め、子供が楽しめそうな候補を共有できる形にする。
現在の子供の年齢は2歳8ヶ月。主な移動手段は徒歩と電車で、自転車・車も利用可能。
移動時間の上限、起点、興味の詳細は未決定。収集・HTML出力の実装を妨げないため、当初は地域と会場を表示し、所要時間は算出しない。

## 要件と範囲

- まず以下の7サイトを調査し、取得できるサイトから順次対応する。
- 開催日時、場所、対象年齢、料金、予約の要否・締切、出典URL、取得日時を保持する。
- 原文の参加条件と「楽しめそう」という推薦判断を区別する。記載のない条件は不明とし、2歳児が参加可能と断定しない。
- 2週間または1ヶ月ごとの実行を想定。実行頻度と、何日先まで掲載するかは別に設定する。
- HTMLを生成し、同じデータから配布用PDF・PNGを生成する。
- 出力に生成日時・対象期間・出典を含め、取得失敗がある場合は不完全な収集だと分かるようにする。

初期の範囲外：公開Webサービス、ログイン、地図・経路検索、通知配信、入力PDF・画像のOCR、AI APIの必須化。
告知が画像・PDFだけに存在する場合は当初の自動抽出対象外とし、元ページへの案内などの扱いを調査時に記録する。

## 比較した構成

| 案 | 利点 | トレードオフ |
| --- | --- | --- |
| Go + Go Modules（選択） | CLI、型のあるデータ整理、標準ツールによる環境整備に適する | ブラウザ出力には別途Chromiumが必要 |
| Python + uv | データ処理の試作や入力文書解析の選択肢が豊富 | 今回はOCRを要件とせず、この強みを優先する必要がない |

ユーザーとGoを使う方針に合意。以降の詳細は実装者の提案であり、本書のレビュー対象。

## 構成案

収集 → 共通イベント形式へ変換 → 対象期間・参加条件の整理と重複除去 → JSON保存 → HTML生成 → PDF・PNG出力。

- mise：Go本体のバージョンをプロジェクトのmise.tomlで固定する。システムへのGoの直接インストールやmiseのグローバル設定は行わない。Go本体はmiseのユーザー用ディレクトリに保存される。シェル全体への有効化を必須とせず、mise execで実行できる手順を用意する。
- Go Modules：ライブラリの依存管理。実装時点の安定版Goを確認してmise.tomlとgo.modのバージョン指定を整合させる。
- net/http + goquery：通常のHTML取得と解析。タイムアウト、再試行上限、アクセス間隔を設ける。
- chromedp：JavaScript実行が必要と確認された情報源、およびChromiumでのPDF・画像出力。
- encoding/json：中間結果保存。まずDBは導入しない。
- html/template：外部ページの文字をエスケープし、HTMLレポートを作る。
- GitHub Actions：CIと、後続Issueでの手動・定期実行。成果物の保存先と保持期間はそのIssueで決める。

取得処理は情報源ごとに分離し、1サイトの障害でも他の結果を保存する。
0件と取得失敗を区別する。日時はAsia/Tokyoで扱い、不明な時刻や年を無条件に補完しない。
出典のタイトル・URLや開催日などを使って重複候補を扱い、同名の別日開催を消さない。

HTMLはスマートフォンで閲覧できる一覧を想定。PDFは印刷用CSSで改ページを調整し、PNGは長大にならない単位に分割する。
具体的な見た目は出力機能のIssueで決める。Chromiumと日本語フォントを実行環境に用意する。

## 初期セットアップ案

- README：目的、前提環境、実行・検証方法、開発順序。
- mise.toml：Goの具体的なバージョンを固定。ローカルとCIで同じ指定を使用する。
- go.mod / go.sum：初期段階で必要な依存だけ追加する。
- CLIの最小骨格と、今後ソース別処理を置ける構成。未実装の収集機能は作らない。
- gofmt、go vet、go test、GitHub Actionsでの同じチェック。
- .gitignore：生成物、キャッシュ、ローカル設定、秘密情報を除外。
- AGENTS.md：日本語ドキュメント、Issue単位の作業、検証方法、取得時の基本方針を記録。
- Issueテンプレート：目的、範囲、完了条件、検証方法。
- skills：既存の汎用skillsを重複コピーしない。ユーザー指定により、Issueの書き方を統一する専用skillを .agents/skills/write-issue/SKILL.md に置き、AGENTS.mdから参照する。

開発ツールを最初から増やしすぎず、追加lint・タスクランナー・Dockerは必要性が生じた時点で検討する。
miseとGo 1.27.3を導入済み。Goはmiseのユーザー用管理ディレクトリに保存し、グローバル設定は変更していない。GitHub CLIの認証はサンドボックス外で確認済み。

## Issueの進め方と検証

詳細は docs/issues/README.md を参照。初期セットアップから1件ずつ実施する。
収集処理は保存したHTMLを使うテストで日時・年齢条件・解析失敗を検証し、実サイトの疎通確認と分ける。
出力では日本語フォント、リンク、改ページ、画像の分割を実物で確認する。
スケジュールは「14日間隔」と「月2回」を同一視せず、希望する頻度を自動化Issueで確定する。
