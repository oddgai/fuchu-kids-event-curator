# PRを作る

実際の差分をレビューする人に向けて、日本語で変更の目的・内容・検証結果をまとめる。

## タイトルと本文

タイトルは変更後の振る舞い・成果を具体的に表し、先頭に連番を付けない。
本文は次の3見出しを基本とする。

- `## 背景`：具体的な問題と必要な理由。関連Issueを `#1` のように参照する。
- `## 変更内容`：最終的な差分と、その結果できること。会話の経緯や採用しなかった案は省く。
- `## 確認方法`：実行したコマンドと結果、確認できていない項目・制約。未実行のCIやテストを成功扱いにしない。

内容が少ない場合は各項目を短い段落にする。複数の変更・確認は箇条書きで示す。
Issueの完了条件をすべて満たす場合は `Closes #1`、一部の対応なら `Refs #1` とする。
自動クローズするIssueは実際の変更範囲と照合する。

## 作成前

- AGENTS.md、PRテンプレート、関連Issue、作業ツリーと比較先との差分を読む。
- 既存PR・ブランチを確認し、重複を避ける。
- `mise run check` を実行する。skillを変更した場合はその検証も行う。
- 生成物・秘密情報・無関係な変更がコミット対象に混ざっていないか確認する。
- 比較先と作業ブランチを分け、通常のpushを使う。force-pushやマージは別途明示の依頼がある場合のみ行う。

PR作成が依頼された場合は必要なコミット・作業ブランチのpush・PR登録まで進める。
原稿だけの依頼ではGitHubへ反映しない。
空のリポジトリでは比較先が存在しないため、空コミットのmainと、その子の作業ブランチを用意する必要があることを説明する。

## GitHubへの反映と確認

本文を一時ファイルに書き、gh pr create / edit の `--body-file` で渡す。
PR作成後はタイトル・本文・base/head・差分を取得し直す。
CIの結果を確認し、失敗した場合は原因を調べて修正する。進行中・実行できない場合はその状態を報告する。
最後にPRのリンクと検証結果を簡潔に伝える。レビューコメントの投稿は依頼に含まれる場合だけ行う。
